# lag_h1 (8 Oct 2026): does the plan's latency make the lag?

## 1. Question

Wesley, 7 Oct: "investigate the cause of the 0.2 second delay. I dont want a bandaid fix like just
sending the reference earlier ... find the actual root cause so we can fix it in a way that is highly
defensible and robust."

## 2. Hypothesis

H1 (overnight lag study): the planner -> tracker cascade has no shared time base.
- Node 0 of each plan is the measured pose.
- The plan is unstamped, and each tracker flies node 0 as "now" until the next plan.
- So the drones are commanded D late (twin 0.11 s, rig 0.145 s).
- The plan recovers only c ~ 0.2 of a gap per 0.5 s, so the steady lag L0 is a multiple of D.

The study confirmed the mechanism in the code, but not its size: the evidence was circular, and at
a fixed D the pull source alone moved L0 by 0.07 s (R1105 vs R1106).

Adding exactly the rig's extra latency to the twin decides it. Prediction, on the 7 Oct-default
orbit:

| metric | baseline (twin) | +0.035 s on every reference publish |
|---|---|---|
| D | ~0.11 s | ~0.145 s (+0.035) |
| L0 | baseline | +0.07 to +0.09 s (2-2.7 x the added delay) |
| c | ~0.2 | unchanged (+-0.03) |

## 3. The one variable

`ref_publish_delay_s` (test-only planner parameter, default 0): each `/drone_i/reference_trajectory`
message is held for this long of sim time before it is published. Nothing else changes: the
trackers, the mocap emulator and the solve are untouched.

| arm | config | code |
|---|---|---|
| base | `w4_orbit_0125.yaml` (even ring, r 0.5, 0.125 m/s, 7 Oct defaults, mode mpc) | week4 |
| H1 | `w4_orbit_0125_delay035.yaml` (+ `ref_publish_delay_s: 0.035`) | `time-cascade` |

## 5. Pass / fail numbers

All on the planner clock, `tools/lag_metrics.py`, the mean of 2 runs per arm.

| metric | supports H1 | falsifies H1 |
|---|---|---|
| D (arm - base) | +0.025 to +0.045 s | < +0.015 s (the knob did not reach the trackers) |
| L0 (arm - base) | >= +0.05 s | < +0.03 s: latency is not what makes the lag |
| c (arm - base) | within +-0.03 | moves more (the amplifier is not independent of the latency) |

If H1 is supported, the time-consistent cascade (card `2026-10-08_time_cascade.md`) is the fix: it
removes D, rather than leading the reference. If it is falsified, the lag is in the plan (c, b0), and
the replay study (H2) comes first.

## 6. Repeats

2 per arm, same host (lab PC), real-time factor logged.

## 7. Cost

2 Gazebo runs (the arm; the base is shared with the safety-defaults card's S1 baseline).

## 8. New code?

Yes: a default-off, test-only parameter in `planner_node._publish_ref`. It queues the message and a
sim-clock timer publishes it when due. There is a unit test. It lives on the `time-cascade` branch,
not week4, and is deleted with the fix if it has no further use. No critic: it is not a control law,
and it is off by default.
